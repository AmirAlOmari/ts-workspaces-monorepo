# 10. `tsc -b` versus Nx for builds

Prev: [9. Roadmap](09-roadmap.md) · Index: [book](README.md)

Question: if TypeScript 7 already builds this graph fast on one machine, does a task runner with a cache (Nx, later maybe Bazel) earn its place, especially for a shared CI cache? This page compares the builds head to head. Raw table: [`bench/nx/RESULTS.md`](../bench/nx/RESULTS.md). Rerun: `bench/nx/run.mjs`.

## Verdict

**Stay on `tsc -b` for building.** On 40 packages and 1,720 files, `tsc -b` is faster than Nx in every scenario measured except a remote-cache restore on a very slow compile, which this graph is not. Nx pays a fixed per-task cost (a process per package, hashing, cache copy) that is larger than TypeScript 7's whole compile. A remote cache is the one thing `tsc -b` cannot do, but the measured restore (about 3 s for 40 packages from a local server) was slower than recompiling (1.9 s). Revisit when the build is dominated by something slower than `tsc` (bundling, codegen, Docker, e2e tests) or when the graph is large enough that TypeScript itself takes minutes.

## Measured (40 packages, 4 cores, Nx 24.0.1, TS 7.0.2)

Node was 22.22.0 in this sandbox, not the template's 24. Median of 3, Nx daemon on unless stated. Nx runs `tsc -p tsconfig.json` per package, ordered by `dependsOn: ["^build"]`.

| Scenario                                            | `tsc -b` |             Nx, default inputs |             Nx, `.d.ts` inputs |
| --------------------------------------------------- | -------: | -----------------------------: | -----------------------------: |
| Cold, no cache                                      |   2.30 s |                         6.00 s |                         6.49 s |
| Nothing changed                                     |   0.09 s | 0.60 s (3.57 s without daemon) | 0.63 s (4.05 s without daemon) |
| Outputs deleted, local cache restore                |      n/a |                         3.55 s |                         3.30 s |
| Body-only change at the bottom of the DAG           |   0.19 s |      3.34 s (15 of 40 rebuilt) |             1.10 s (1 rebuilt) |
| API change at the bottom of the DAG                 |   0.24 s |            3.09 s (15 rebuilt) |             1.45 s (3 rebuilt) |
| Change at the top of the DAG                        |   0.19 s |                         1.01 s |                         0.99 s |
| Fresh checkout with restored `dist` + `tsbuildinfo` |   0.12 s |                            n/a |                            n/a |

Most numbers have a fixed floor: Nx start-up and graph work cost roughly 0.5 s with the daemon and 3 s without it (CI disables the daemon by default).

## The four properties you asked about

**Caching.** `tsc -b` caches through `tsbuildinfo` next to each project, which is an incremental compiler state, not a content-addressed artifact. Nx hashes task inputs (files, dependency hashes, tool versions, env) and stores outputs by hash, so any previous state is restorable, on any machine. The `tsc -b` cache is one entry per project and valid only for the latest state of the tree. A surprise in our favour: in a fresh checkout whose sources are newer than the restored `dist`, TS 7 `tsc -b` finished in 0.12 s, so it decides by content (buildinfo hashes) and not file times, and the existing GitHub/GitLab `dist` + `tsbuildinfo` cache works across checkouts. Verified only for TS 7; **TS 6 to verify** (older versions compared file times).

**Fine-grained invalidation.** This is where the defaults differ most. Nx's default input for a dependent includes the dependency's _sources_, so a one-line body change in `pkg-000` invalidated 15 downstream packages (3.34 s), while `tsc -b` rebuilt almost nothing (0.19 s) because it compares the emitted `.d.ts`. Nx can match that if you hash dependency _outputs_: `{ "dependentTasksOutputFiles": "**/*.d.ts", "transitive": false }` as an input. With it a body change rebuilt 1 package (1.10 s) and an API change 3. Caveat, **to verify**: with `transitive: false`, a package that re-exports another package's types (`export * from "@acme/a"`) has an unchanged `.d.ts` text while the types behind it changed, so dependents could reuse a stale result. `transitive: true` is safe but loses most of the cutoff on an API change (25 of 40 rebuilt, 2.72 s). The generated bench graph has no re-exports, so it cannot show the stale case.

**Parallel execution of the DAG.** Both run independent projects concurrently. Nx runs one `tsc` process per project (`--parallel` defaults to 3; we set 4), critical path 2.5 s here; TS 7 builds the graph inside one process with native threads (`--builders`, see [2](02-typescript.md#parallelism)). On a 4-core machine with a fast compiler, process-per-task overhead dominates: 6.0 s versus 2.3 s cold. Nx would win if each task were slow and the graph wide.

**Shared CI cache.** `tsc -b` has no shared cache; the best equivalent is restoring `dist` + `tsbuildinfo` from the CI cache ([6](06-ci.md)), which works per branch/key. Nx options:

- **Nx Cloud:** hosted, or Nx Enterprise for on-prem. Pricing not looked up.
- **Self-hosted server implementing Nx's OpenAPI contract** (`GET`/`PUT /v1/cache/{hash}` with a bearer token; env `NX_SELF_HOSTED_REMOTE_CACHE_SERVER` and `NX_SELF_HOSTED_REMOTE_CACHE_ACCESS_TOKEN`). You write or deploy the server and its storage/auth. Source: [Nx docs](https://nx.dev/docs/guides/tasks--caching/self-hosted-caching). Verified here with a 30-line test server (`bench/nx/cache-server.mjs`): a second clone in another directory got 40 of 40 remote hits, so hashes are path-independent. Entries total 612 KB for 40 packages.
- **Ready-made storage plugins** (`@nx/s3-cache`, `@nx/gcs-cache`, `@nx/azure-cache`, `@nx/shared-fs-cache`): whether they need a paid licence was not confirmed from the docs (**to verify** before relying on them).
- For a private GitLab: a small server in front of an S3-compatible bucket or a shared volume, or a ready-made container image. Not tried.

Observed behaviour worth knowing: with the remote URL unreachable, Nx failed the whole run with "Failed to send request" rather than building without the cache. **Retry/fallback settings to verify.** The remote restore (2.9–3.9 s wall, localhost) was slower than `tsc -b` cold (1.9 s).

## Other facts

- **Script hop:** a package script `"build": "tsc -p tsconfig.json"` run through `pnpm run` took 13–18 s for the same 40 tasks; declaring the command in `package.json#nx.targets` (no package-manager process) took 4.8 s. If you adopt Nx, do not route through `pnpm run`.
- **Build order is still required.** A single `tsc -p` without built dependencies fails (TS6305); Nx's `dependsOn: ["^build"]` supplies the order that `tsc -b` derives from `references`. Nx has its own TypeScript project-reference sync (`@nx/js`); whether it can replace `scripts/sync-refs.mjs` was **not tried**.
- **Cost:** `nx` is a new dependency tree, a second graph (Nx infers projects from `package.json`, so it agrees with pnpm), and a place where cache correctness depends on declared inputs. `tsc -b` has no declared inputs to get wrong.
- Not measured: `nx affected`, watch mode, test/lint targets cached by Nx (this is where Nx plausibly pays off: Vitest, linting, and codegen are cacheable tasks with expensive outputs), big graphs (hundreds of packages), network-latent remote cache.

## When Nx earns its place

1. The pipeline has slow, cacheable tasks beyond `tsc` (bundling, codegen, e2e), shared by CI runs and developers.
2. A graph large enough that TS itself takes minutes, so skipping whole projects by hash beats any single-process compile.
3. You want `affected`-only CI on pull requests.

If you adopt it, keep `tsc -b` as the local and typecheck path, put Nx on top for the other targets, and use `.d.ts` inputs only after resolving the re-export caveat above.

## Bazel

Mentioned only: it would add hermetic, remote-executable builds and a very strong shared cache, at the price of BUILD files for every package and a toolchain (`rules_ts` over `tsc`/project references) of its own. Not tried; a later step if the repo outgrows Nx.
